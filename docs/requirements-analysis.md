# AI 热点信息每日汇总项目需求分析

分析日期：2026-09-01

关联文档：

## 0. 已确认需求澄清

确认日期：2026-09-01

本轮已确认以下关键产品决策：

- 首期开始即支持多用户，而不是单用户或本地管理员工具。
- 部署形态面向外公网部署，而不是只支持本地或内网运行。
- LLM 能力需要兼容多厂商，通过统一接口接入不同模型服务商。
- 首期数据源都支持，即 RSS、Hacker News、GitHub、arXiv、Product Hunt、Hugging Face 都纳入 MVP。
- 当前阶段只做 Web 看板，不做 Email、RSS、Telegram、飞书、企业微信等推送渠道。
- 内容自动发布到 Web 看板，不设置人工审核发布流程。
- 输出语言为中文摘要；输入来源可以是中文或英文。

## 1. 项目背景

AI 领域信息更新速度快，信息源分散在官方博客、技术社区、开源平台、论文平台、产品发布平台和社交媒体中。对开发者、产品经理、创业者、投资研究人员和 AI 爱好者来说，每天主动浏览所有来源成本很高，而且重复信息多、质量参差不齐。

本项目希望建设一个“AI 情报聚合与每日简报平台”，通过自动采集、去重、评分、摘要、分类和分发，帮助用户快速了解当天真正值得关注的 AI 热点。

项目不应只停留在“定时生成 Markdown 日报”的脚本形态，而应提供可持续使用的前后端产品能力，包括多用户登录、信息工作台、来源管理、历史归档、搜索筛选和后续分发扩展能力。

## 2. 产品定位

### 2.1 一句话定位

面向关注 AI 动态的多用户 Web 平台，自动聚合多来源 AI 热点，生成可追溯、可筛选、可回看的中文每日情报简报。

### 2.2 核心价值

- 降低信息筛选成本：用户不需要每天手动浏览多个网站。
- 提升信息质量：通过来源权重、热度信号和 LLM 评分过滤低价值内容。
- 减少重复阅读：把同一事件的多来源报道聚合成一个 topic。
- 提供中文摘要：让用户快速理解英文新闻、论文和开源项目。
- 保留可追溯性：每条摘要都能回到原始来源。
- 支持长期复盘：保存历史日报和热点趋势，方便回看。

### 2.3 产品形态

首期产品形态确认为面向外公网部署的 Web 应用：

- 后端负责采集、处理、摘要、评分、入库和 API。
- 前端负责多用户登录、日报展示、条目查询、来源管理和任务状态展示。
- 定时任务每天自动生成 digest，并自动发布到 Web 看板。
- LLM 通过统一 provider 接口兼容多厂商模型服务。
- 当前阶段不做邮件、RSS、Telegram、飞书、企业微信等推送渠道。

核心诉求：

- 找到可借鉴的产品方向。

- 找到能马上使用的新产品。

## 4. 用户痛点

### 4.1 信息源分散

AI 信息散落在多个平台：

- 官方博客。
- Hacker News。
- GitHub。
- arXiv。
- Hugging Face。
- Product Hunt。
- 新闻媒体。
- Newsletter。
- 社交媒体。

用户通常需要打开很多页面才能形成当天全局认知。

### 4.2 重复信息多

同一事件可能被多个来源转发和改写。例如一次模型发布，可能同时出现在官方博客、HN、GitHub、媒体新闻和多个 newsletter 中。如果没有聚类能力，用户会反复阅读相似内容。

### 4.3 信息质量不稳定

AI 内容里存在大量标题党、营销稿、重复转载、浅层工具推荐。用户需要判断哪些内容真正重要。

### 4.4 英文阅读成本高

大量高质量信息来自英文来源，包括论文、开源项目 README、官方博客和 HN 讨论。中文用户需要摘要和解释，而不只是机器翻译。

### 4.5 缺少历史复盘

普通 newsletter 发完即走，不适合检索过去某天、某类主题或某个关键词的趋势。

## 5. 用户场景

### 5.1 每日晨间浏览

用户每天早上打开系统首页，查看今日 AI 热点。系统按分类展示重点事件，每条内容包含标题、摘要、来源、热度和“为什么重要”。

成功标准：

- 3-5 分钟内理解当天主要 AI 动态。
- 可以快速打开原文深入阅读。
- 不需要手动访问多个信息源。

### 5.2 发现开源项目

开发者进入“开源项目”分类，查看过去 24 小时 GitHub 热门 AI 项目，按 stars today、语言、topic、摘要筛选。

成功标准：

- 能识别项目用途、热度和技术栈。
- 能查看 README 摘要和仓库链接。
- 可以收藏后续跟踪。

### 5.3 追踪特定主题

用户搜索 “RAG”、“Agent”、“OpenAI”、“Claude Code” 等关键词，查看相关条目和历史趋势。

成功标准：

- 搜索结果按相关性和时间排序。
- 同一事件被聚合到同一 topic。
- 可以查看该 topic 的相关来源。

### 5.4 配置信息源

管理员在来源管理页新增或关闭某个 RSS/API source，查看最近抓取是否成功。

成功标准：

- 来源可以启用/禁用。
- 抓取失败原因可见。
- 可以手动触发一次抓取验证。

### 5.5 生成每日 Web 简报

系统每天固定时间生成日报，并自动发布到 Web 看板。

成功标准：

- 生成内容稳定。
- 每条内容带原文链接。
- 发布失败有日志和重试机制。
- 用户登录后可以查看今日和历史简报。

## 6. 需求范围

### 6.1 首期目标

首期目标是完成“采集 -> 入库 -> 去重 -> 摘要 -> 排序 -> 前端展示”的闭环。

必须能回答：

- 今天有哪些 AI 热点？
- 每条热点为什么重要？
- 来源是什么？
- 哪些内容来自 RSS、HN、GitHub、arXiv、Product Hunt、Hugging Face？
- 过去的日报能否回看？
- 管理员能否知道采集任务是否成功？
- 不同用户能否登录并查看 Web 看板？
- 用户能否配置自己的关注规则并影响个人看板排序？

### 6.2 明确不做

首期不做以下能力：

- 企业级组织、多租户空间和复杂 RBAC。
- 移动端 App。
- 浏览器插件。
- 音频日报。
- 付费订阅系统。
- 复杂推荐算法。
- 全网无限制爬虫。
- 普通用户自定义外部 URL 信息源。
- 普通用户发起任意外部平台实时检索。
- 大规模向量检索平台。
- 社交平台深度抓取。
- Email、RSS、Telegram、飞书、企业微信等推送渠道。

### 6.3 后续可扩展

后续可以扩展：

- 高级个性化偏好。
- 个人订阅频道。
- 用户自定义外部信息源。
- 外部关键词实时检索。
- 主题趋势图。
- embedding 聚类。
- Telegram/飞书/企业微信推送。
- Email 和 RSS 分发。
- 周报/月报。
- MCP/API 对外服务。
- 语音播报。

## 7. 功能需求

### 7.1 信息源管理

#### 需求描述

系统需要维护一组可配置的信息源，用于自动采集 AI 相关新闻、项目、论文和产品发布。

#### 功能点

- 新增 RSS source。
- 查看 source 列表。
- 启用/禁用 source。
- 设置 source 类型。
- 设置 source 权重。
- 记录最近抓取时间。
- 记录最近错误信息。
- 支持手动触发单个 source 抓取。

#### 首期 source 类型

- RSS。
- Hacker News。
- GitHub。
- arXiv。
- Product Hunt。
- Hugging Face。

#### 后续 source 类型

- 自定义网页。
- Newsletter inbox。
- 社交媒体或 KOL source。

#### 验收标准

- 管理员可以看到所有启用 source。
- 管理员可以知道每个 source 最近一次抓取结果。
- 禁用后的 source 不再参与定时抓取。

### 7.2 数据采集

#### 需求描述

系统需要定时从不同来源拉取原始信息，并保存原始字段，方便追溯和后续重新处理。

#### 功能点

- 支持定时任务采集。
- 支持手动触发采集。
- 支持抓取失败日志。
- 支持重复抓取防重。
- 保存 raw payload。
- 保存 canonical url。
- 保存发布时间和抓取时间。

#### 首期采集源

- RSS：官方博客、技术媒体、AI newsletter feed。
- Hacker News：通过关键词查询 AI 相关内容。
- GitHub：查询 AI 相关热门项目或 topic。
- arXiv：查询 AI、机器学习、自然语言处理、计算机视觉等分类论文。
- Product Hunt：查询 AI 产品发布和热度数据。
- Hugging Face：查询模型、数据集和 Spaces 趋势。

#### 验收标准

- 每次采集任务有开始时间、结束时间、状态和错误信息。
- 同一 URL 不会重复入库为多个有效条目。
- 采集失败不会中断其他 source。

### 7.3 数据标准化

#### 需求描述

不同来源的数据结构不同，需要统一成内部 item 模型。

#### 标准字段

- 标题。
- 原文 URL。
- canonical URL。
- 来源。
- 作者。
- 发布时间。
- 抓取时间。
- 来源类型。
- 原始摘要。
- 原始正文。
- 原始 payload。
- 内容 hash。

#### 验收标准

- 前端不需要关心数据来自 RSS、HN、GitHub、arXiv、Product Hunt 还是 Hugging Face。
- 所有 item 至少包含标题、URL、来源和抓取时间。
- 缺失字段要允许为空，但不能导致处理任务失败。

### 7.4 去重与聚类

#### 需求描述

系统需要识别重复条目和相似事件，避免日报中出现大量重复内容。

#### 首期策略

- URL 完全匹配去重。
- canonical URL 去重。
- 标题归一化 hash 去重。
- 同 source external id 去重。
- 轻量 topic 聚合，把同一事件的多来源内容挂到同一专题下。
- topic 聚合作为今日简报、历史简报和详情抽屉中的展示能力，MVP 不单独做热点专题一级页面。

#### 后续策略

- 标题相似度。
- embedding 相似度。
- LLM 判断同一事件。
- 跨天 topic 聚类。

#### 验收标准

- 同一个 URL 多次抓取只展示一次。
- 同一个 GitHub repo 多次进入趋势，只更新热度和最近出现时间。
- 去重规则不会直接删除 raw data，而是保留原始记录和合并关系。
- 同一事件的相关来源可以在详情抽屉中聚合展示。

### 7.5 分类

#### 需求描述

系统需要把条目归类，便于用户浏览。

#### 首期分类

- 模型与大厂动态。
- 开源项目。
- 论文研究。
- 产品发布。
- 工具与教程。
- 行业与融资。
- 社区讨论。

#### 分类方式

首期可采用规则 + LLM：

- GitHub 来源默认倾向开源项目。
- arXiv 来源默认倾向论文研究。
- Product Hunt 来源默认倾向产品发布。
- Hugging Face 来源默认倾向模型、数据集或 AI 应用。
- RSS/HN 通过关键词和 LLM 判断。

#### 验收标准

- 每条进入 digest 的 item 必须有分类。
- 首页能按分类展示内容。
- 用户可以按分类筛选。

### 7.6 热度评分

#### 需求描述

系统需要为每个 item/topic 生成热度评分，用于排序和筛选。

#### 评分因素

- 来源权重。
- 新鲜度。
- 社区热度。
- 关键词相关性。
- 是否来自官方源。
- 是否重复出现于多个来源。
- LLM 重要性评分。

#### 首期建议

先使用可解释规则评分，不引入复杂模型。

示例因素：

- RSS 官方源：较高基础分。
- HN points/comments：转化为热度分。
- GitHub stars/forks/recent activity：转化为热度分。
- Product Hunt votes/comments：转化为产品热度分。
- Hugging Face likes/downloads：转化为模型或数据集热度分。
- arXiv 发布时间、分类和关键词：转化为研究相关性分。
- 最近 24 小时内容：新鲜度更高。
- 命中核心关键词：增加相关性分。

#### 验收标准

- 列表默认按 score 降序。
- score 的主要来源可解释。
- 低分内容不会进入每日 digest，但可以在信息库查看。
- 个性化排序基于全局 score 叠加用户关注、屏蔽和反馈规则，不改变全局 score。

### 7.7 LLM 摘要

#### 需求描述

系统需要通过多厂商兼容的 LLM provider 接口，对高价值条目生成中文摘要、分类和“为什么重要”。

#### 输入

- 标题。
- 原始摘要。
- 正文片段。
- 来源类型。
- URL。
- 社区热度数据。

#### 输出

- 中文一句话摘要。
- 详细摘要。
- 为什么重要。
- 分类。
- 关键词标签。
- 置信度。
- 是否需要人工复核。

#### 成本控制

- 不对所有 raw items 调用 LLM。
- 先基于规则筛掉低价值条目。
- 对同一 content hash 复用结果。
- 保存 provider、模型名、prompt 版本和调用成本，方便回溯。

#### 验收标准

- 进入 digest 的 item 必须有中文摘要。
- 摘要不能缺少原文链接。
- 摘要失败时，系统可以用原始摘要兜底并标记状态。

### 7.8 每日 Digest

#### 需求描述

系统每天生成一份 AI 热点简报。

#### 内容结构

- 今日重点。
- 专题卡片。
- 模型与大厂动态。
- 开源项目。
- 论文研究。
- 产品发布。
- 社区讨论。

#### 每条内容展示

- 标题。
- 中文摘要。
- 为什么重要。
- 来源。
- 发布时间。
- 原文链接。
- 分类。
- 热度分。
- 来源数量。
- 来源特有热度指标。

#### 生成规则

- 每天固定时间生成。
- 生成后自动发布到 Web 看板。
- 支持手动重新生成。
- 每个分类限制展示数量。
- 支持过滤低置信度摘要。
- 支持保存历史版本。

#### 验收标准

- 首页能展示当天 digest。
- 历史页能查看指定日期 digest。
- 手动重新生成不会丢失原始 items。
- 同一事件的多来源内容可以通过专题卡片或详情抽屉查看。

### 7.9 前端首页

#### 需求描述

首页是用户最常访问的页面，用于快速浏览今日 AI 热点。

#### 页面模块

- 日期选择。
- 今日摘要概览。
- 今日重点列表。
- 专题卡片列表。
- 分类内容区。
- 系统精选/我的关注视图切换。
- 热度排序。
- 来源筛选。
- 搜索入口。

#### 交互

- 点击条目打开详情。
- 点击来源跳转原文。
- 按分类筛选。
- 按来源筛选。
- 按时间回看。
- 切换“我的关注”视图。
- 点击“多看类似”“少看类似”“屏蔽来源”记录反馈。

#### 验收标准

- 用户登录并打开首页即可看到今日 digest。
- 无 digest 时显示清晰空状态和手动生成入口。
- 页面不依赖手动刷新才能看到最新生成结果。
- 我的关注视图会应用用户关注、排除、屏蔽和反馈规则。

### 7.10 条目详情

#### 需求描述

用户需要查看单条信息的完整上下文。

#### 展示字段

- 标题。
- 原文 URL。
- 来源。
- 发布时间。
- 抓取时间。
- 中文摘要。
- 为什么重要。
- 分类。
- 标签。
- 热度分。
- 相关条目。
- 专题摘要。
- 事件时间线。
- 原始摘要或正文片段。

#### 验收标准

- 用户可以从 digest、历史简报和信息库进入详情。
- 详情页或抽屉能展示原始来源和处理结果。
- 如果条目属于 topic，能看到相关来源。
- 热点专题不作为 MVP 独立页面，而是在详情抽屉中展示聚合信息。

### 7.11 信息库

#### 需求描述

信息库是系统已采集内容的全量检索入口。它区别于历史简报：历史简报只展示按天生成的精选 digest，信息库展示所有已采集入库内容，包括入选、未入选、低分、待摘要、摘要失败和重复聚合来源。

#### 功能点

- 按来源筛选。
- 按分类筛选。
- 按处理状态筛选。
- 按时间范围筛选。
- 按来源类型筛选。
- 按分数排序。
- 关键词搜索标题、摘要、标签和来源。
- 保存当前站内搜索为关注规则。

#### 验收标准

- 低分或未摘要内容仍可被查到。
- 能定位采集、处理、摘要失败的条目。
- 信息库搜索只查询已采集入库内容，不直接触发外部平台实时检索。
- 保存搜索后，可以在“我的关注”中查看和管理该规则。

### 7.12 任务状态和日志

#### 需求描述

系统需要展示采集和处理任务状态，方便排查问题。

#### 功能点

- 查看最近任务。
- 查看任务状态。
- 查看任务耗时。
- 查看失败原因。
- 支持手动重跑。

#### 验收标准

- 抓取失败、摘要失败、digest 生成失败都有状态记录。
- 单个 source 失败不会影响整体日报生成。

### 7.13 用户账号与权限

#### 需求描述

系统首期即支持多用户访问外公网 Web 看板，并区分普通用户和管理员。

#### 功能点

- 用户账号只能由管理员创建。
- 用户登录和退出。
- 普通用户可以查看今日简报、历史简报、信息库、条目详情和搜索筛选。
- 普通用户可以配置我的关注规则、保存站内搜索和提交反馈。
- 普通用户不能添加自定义外部 URL 信息源，也不能发起任意外部平台实时检索。
- 管理员可以创建和管理用户、管理 source、触发采集、生成 digest、查看任务日志。
- 用户偏好可按用户保存，但首期只要求基础字段。

#### 首期角色

- `user`：查看 Web 看板和内容详情。
- `admin`：管理来源、任务、摘要和系统配置。

#### 验收标准

- 未登录用户不能访问看板页面和管理 API。
- 普通用户不能访问 source 管理和任务重跑接口。
- 系统不提供公开注册入口。
- 管理员可以查看和管理所有 source 与 job run。

### 7.14 我的关注

#### 需求描述

我的关注是用户级个性化规则中心，用于影响当前用户的信息排序、默认筛选和隐藏规则，不改变全局采集范围和全局 digest。

#### 功能点

- 关注关键词：软加权。
- 排除关键词：硬过滤。
- 关注分类：我的关注视图默认筛选，并参与轻量排序加权。
- 关注来源类型：我的关注视图默认筛选。
- 关闭来源类型：硬过滤。
- 屏蔽来源：硬过滤。
- 保存搜索：把信息库中的站内搜索条件保存为关注规则。
- 反馈记录：保存多看类似、少看类似和屏蔽来源操作。

#### 规则说明

- 关注关键词命中标题、摘要、标签或来源时，提高当前用户的个性化排序。
- 排除关键词命中内容时，从当前用户的个性化视图中隐藏。
- 屏蔽来源后，该来源内容不再出现在当前用户的个性化视图中。
- 保存搜索只基于已采集入库内容，不触发外部平台实时检索。
- 多看类似和少看类似会影响相似分类、标签、来源类型和关键词的个性化权重。

#### 验收标准

- 用户保存关注规则后，可以在“我的关注”视图看到匹配内容。
- 排除关键词和屏蔽来源对当前用户生效。
- 用户反馈只影响当前用户，不影响其他用户。
- 普通用户不能通过“我的关注”添加外部 URL 信息源。

### 7.15 LLM Provider 配置

#### 需求描述

系统需要兼容多厂商 LLM 服务，摘要、分类和重要性判断不能写死到单一厂商或单一模型。

#### 功能点

- 支持配置多个 LLM provider。
- 支持设置默认 provider。
- 支持配置模型名、base URL、超时时间、重试次数和是否启用。
- 支持 OpenAI-compatible API 作为通用接入方式。
- 支持记录每次摘要使用的 provider、模型名、prompt 版本和调用状态。
- 支持管理员测试 provider 可用性。

#### 首期 provider 类型

- OpenAI-compatible。
- 后续可按需增加特定厂商适配器。

#### 验收标准

- 摘要模块只依赖统一 provider 接口。
- 更换默认 provider 不需要修改摘要业务代码。
- provider 调用失败时有错误日志，并可回退到备用 provider 或标记摘要失败。

## 8. 非功能需求

### 8.1 可用性

- 每日自动任务应稳定运行。
- 采集失败应可重试。
- 单个来源失败不影响其他来源。
- 前端应能清楚展示空状态、加载状态和失败状态。

### 8.2 性能

首期目标：

- 首页简报数据响应小于 1 秒。
- 信息库列表数据响应小于 2 秒。
- 单次采集任务在 5-10 分钟内完成。
- 每日 digest 生成在 5 分钟内完成。

### 8.3 可维护性

- 不同 source 采集器应实现统一接口。
- LLM prompt 应版本化。
- 评分规则应集中配置。
- 数据处理任务应有明确状态机。
- 后端 API、采集任务和前端页面应解耦。

### 8.4 可追溯性

- 保留 raw payload。
- 保留原文 URL。
- 保留来源 ID。
- 保留摘要模型和 prompt 版本。
- 保留处理时间和错误信息。

### 8.5 成本控制

- LLM 调用前先进行规则筛选。
- 相同内容不重复摘要。
- 正文抽取只对高价值条目执行。
- 任务失败要避免无限重试。

### 8.6 安全性

- API key 不进入代码仓库。
- 后端管理接口需要鉴权。
- 外公网部署必须启用用户认证。
- 用户密码需要加密存储。
- LLM provider key 需要通过环境变量或密钥配置管理，不在前端暴露。
- 外部 URL 抓取需要限制超时和响应大小。
- 前端展示外部内容时要避免 XSS。
- 用户配置和系统配置要区分权限。

## 9. 数据需求

### 9.1 核心实体

- User：用户账号。
- AuthSession：登录会话或令牌。
- Source：信息源。
- RawItem：原始采集条目。
- Item：标准化和处理后的条目。
- Topic：聚合后的热点事件。
- Digest：每日简报。
- DigestItem：简报和条目的关系。
- JobRun：任务执行记录。
- LLMProvider：LLM 服务商配置。
- UserPreference：用户偏好。
- SavedSearch：用户保存的站内搜索规则。
- UserFeedback：用户对内容的偏好反馈。

### 9.2 数据状态

Item 建议包含以下处理状态：

- `collected`：已采集。
- `normalized`：已标准化。
- `deduped`：已完成去重。
- `ranked`：已评分。
- `summarized`：已摘要。
- `selected`：入选 digest。
- `failed`：处理失败。

### 9.3 数据保留

- raw payload 建议长期保留，便于重新处理。
- digest 历史版本建议长期保留。
- 失败日志至少保留 30 天。
- 高频抓取的临时正文可以设置清理策略。

## 14. 关键风险

### 14.1 信息源稳定性

风险：

- 部分来源没有稳定 API。
- 网页结构变化会导致抓取失败。

应对：

- 优先使用 RSS/API。
- 每个 source 独立失败。
- 保留错误日志和手动重试。

### 14.2 LLM 成本和质量

风险：

- 对所有内容摘要成本高。
- 摘要可能出现误解或过度推断。
- 多厂商模型能力、价格、速率限制和输出格式存在差异。

应对：

- 先规则筛选再摘要。
- 摘要输出要保留置信度。
- 保留原文链接和原始摘要。
- Prompt 版本化。
- 通过统一 provider 接口、超时、重试和备用 provider 降低厂商绑定风险。

### 14.3 去重难度

风险：

- 同一事件不同标题、不同 URL，简单 hash 无法识别。
- 专题聚合如果做成独立页面，会和今日简报产生信息架构重叠。

应对：

- MVP 先做 URL/hash 去重和轻量 topic 聚合。
- 热点专题不作为独立一级页面，先并入今日简报、历史简报和详情抽屉。
- 后续再做标题相似度和 embedding 聚类。

### 14.4 范围膨胀

风险：

- 很容易同时想做 newsletter、搜索、推荐、社交抓取、移动端、推送渠道和复杂权限。
- 普通用户自定义外部 URL 或任意外部实时检索，会增加安全、成本和滥用风险。

应对：

- 首期只做多用户 Web 看板、采集处理闭环和规则型我的关注。
- 普通用户只能做站内搜索、保存搜索和个性化规则配置。
- 推送、深度个性化、音频、企业级组织权限、用户自定义外部源等放到后续版本。

- 热点专题不作为独立一级页面，先并入今日简报、历史简报和详情抽屉。
- 当前只做 Web 看板，不做推送渠道。
- 内容自动发布到 Web 看板。
- 输出语言为中文摘要。
- 生产部署形态为单台云服务器，并通过 HTTPS 反向代理对外提供 Web 和 API。
- 外部 API token 允许管理员后台录入，后端加密保存。
- Digest 默认北京时间每天 08:00 生成，调度时间可配置。

### 16.2 已确认默认值

以下实现细节按推荐方案确认：

- 首个管理员账号通过一次性 `create-admin` 命令创建。
- 首批默认 source 每类预置 1-3 个最小可用配置，后续管理员可在后台调整。
- `raw_items`、`llm_call_logs`、`job_runs` 默认保留 180 天。
- `items`、`topics`、`digests` 默认长期保留。
- PostgreSQL 每日备份一次，默认保留 14 天。

## 17. 推荐决策

基于当前调研和需求分析，建议做如下产品决策：

- 首期定位：支持多用户访问的 AI 情报 Web 看板。
- 首期语言：中英文来源采集，中文摘要输出。
- 首期信源：RSS、Hacker News、GitHub、arXiv、Product Hunt、Hugging Face。
- 首期前端：登录、今日简报、历史简报、信息库、我的关注、来源管理、任务日志、LLM provider 配置、用户管理。
- 首期后端：FastAPI、PostgreSQL、APScheduler。
- 首期部署：支持外公网部署，并提供 Docker Compose 起步方案。
- 首期摘要：只对高分候选内容调用 LLM。
- 首期 LLM：统一 provider 接口，兼容多厂商。
- 首期去重：URL/hash 去重和轻量 topic 聚合，专题聚合先体现在详情抽屉和简报卡片中。
- 首期个性化：我的关注采用规则型硬过滤和软加权，不做复杂推荐算法。
- 首期发布：digest 自动发布到 Web 看板，不做人工审核流程。
- 首期推送：不做 Email、RSS、Telegram、飞书、企业微信等推送渠道。

这个范围比最小单用户版本更重，但符合外公网产品化方向。实现时应优先保证账号、安全、采集闭环和 Web 看板可用，再迭代高级聚类、个性化和推送渠道。
