## 1. 评审背景

本次评审用于确认 AI 热点信息每日汇总系统的需求分析是否覆盖以下内容：

- 明确业务目标：为什么做这个系统。
- 确定用户角色：谁使用。
- 梳理业务流程：用户和系统如何操作。
- 收集功能需求：系统需要哪些功能。
- 分析非功能需求：性能、安全、稳定性、兼容性等。
- 输出需求说明书、业务流程图、原型图和需求评审记录。

## 5. 评审发现

### 5.1 范围复杂度高于最小 MVP

首期同时支持多用户、外公网部署、六类数据源和多厂商 LLM，会明显增加架构和研发复杂度。

处理意见：

- 保留这些能力在 MVP 范围内。
- 实施时按优先级分阶段推进：账号与安全、数据模型、采集闭环、摘要与 digest、Web 看板。
- 六类数据源都进入首期，但每类先实现最小可用 collector。

### 5.2 Product Hunt 等 API 存在 token 和授权风险

Product Hunt、GitHub、Hugging Face 等来源可能需要 token 或受 rate limit 影响。

处理意见：

- source 需要支持未配置 token 的状态展示。
- 对外部 API 调用做错误处理和限流。
- README 和部署文档中明确 token 配置方式。

### 5.3 LLM 多厂商兼容需要统一抽象

如果摘要模块直接依赖单一 SDK，后续切换厂商成本高。

处理意见：

- 首期定义统一 LLM provider 接口。
- 优先支持 OpenAI-compatible API。
- 记录 provider、模型名、prompt 版本和调用状态。

### 5.4 外公网部署要求基础安全前置

外公网部署不能把认证、安全和权限放到后期。

处理意见：

- 首期必须实现登录认证。
- 管理接口必须校验 admin 角色。
- 密码必须加密存储。
- API key 和 provider key 不进入代码仓库，不暴露到浏览器。

### 5.5 信息平台页面结构需要避免重叠

今日简报、历史简报、信息库和热点专题存在潜在重叠，需要明确职责边界。

处理意见：

- 今日简报负责当天精选内容。
- 历史简报负责按日期查看已发布 digest。
- 信息库负责全量已采集内容检索。
- 热点专题不作为独立页面，先作为专题卡片和详情抽屉中的聚合信息。

### 5.6 我的关注应是规则中心

我的关注不能简单等同于关键词硬匹配，否则容易漏掉相关内容。

处理意见：

- 关注关键词、关注分类和多看类似采用软加权。
- 排除关键词、屏蔽来源和关闭来源类型采用硬过滤。
- 保存搜索只保存站内检索条件，不触发外部实时抓取。
- 普通用户不能添加外部 URL 信息源。
